## 1. 메모리 저장 단위와 엔디언

- 메모리는 **주소 하나에 1바이트**가 저장된다 (바이트 주소 지정).
- "32bit / 64bit"는 메모리 한 칸 크기가 아니라 **CPU 워드 크기와 주소 폭**을 의미한다.
- 4바이트 `int`는 **연속된 주소 4칸**에 나뉘어 저장되며, 바이트 순서를 정하는 규칙이 **엔디언(endianness)**이다.

`int x = 0x12345678;` 을 주소 `0x1000`에 저장할 때:

| 주소 | 0x1000 | 0x1001 | 0x1002 | 0x1003 |
|---|---|---|---|---|
| 리틀 엔디언 (x86, 대부분의 ARM) | 78 | 56 | 34 | 12 |
| 빅 엔디언 (네트워크 바이트 순서) | 12 | 34 | 56 | 78 |

- **리틀 엔디언**: 하위 바이트(LSB)를 낮은 주소에 저장
- **빅 엔디언**: 상위 바이트(MSB)를 낮은 주소에 저장

같은 CPU 안에서는 저장·읽기 규칙이 같으므로 값이 올바르게 읽힌다. 문제가 되는 경우:

- 네트워크 통신 → `htons()`, `htonl()`로 변환
- 엔디언이 다른 시스템끼리 바이너리 파일 교환
- `char *`로 바이트 단위로 메모리를 들여다볼 때 (디버거 메모리 뷰)

예: 16비트 `0x0001`을 리틀 엔디언으로 저장하면 `01 00`. 이를 빅 엔디언으로 읽으면 `0x0100` (= 256).

## 2. 포인터 연산과 바이트 단위 접근

### 엔디언 확인 코드

```c
#include <stdio.h>

int main(void) {
    unsigned int a = 0x12345678;
    unsigned char *p = (unsigned char *)&a;   // 반드시 char 포인터

    for (int i = 0; i < 4; i++) {
        printf("%p: %02X\n", (void *)(p + i), p[i]);
    }

    printf(p[0] == 0x78 ? "little-endian\n" : "big-endian\n");
    return 0;
}
```

실행 결과 (Windows x86-64):

```
0000005C435FFE9C: 78
0000005C435FFE9D: 56
0000005C435FFE9E: 34
0000005C435FFE9F: 12
little-endian
```

### 처음에 했던 실수: `unsigned int *` 사용

```c
unsigned int *p = (unsigned int *)&a;   // ❌
```

```
0000005C435FFE9C: 12345678
0000005C435FFEA0: 435FFE9C
0000005C435FFEA4: 5C
0000005C435FFEA8: 435FFED8
big-endian
```

문제점:

1. **포인터 연산은 가리키는 타입 크기만큼 이동**한다. `int *`라서 `p + 1`이 +4바이트 (주소가 `9C → A0 → A4 → A8`).
2. `p[0]`은 바이트가 아니라 **이미 조립된 int 전체** (`0x12345678`). 그래서 `p[0] == 0x78`이 거짓 → **잘못 "big-endian"으로 판정**.
3. `p[1]`~`p[3]`은 `a` 바깥 메모리를 읽음 → **정의되지 않은 동작(UB)**. 출력된 값은 스택에 남아 있던 쓰레기값 (`a`의 주소 조각 등).

> `%02X`는 "최소 2자리"라는 뜻이라 더 긴 값은 자르지 않고 전부 출력된다.

## 3. `%p`와 `(void *)` 캐스팅

- `printf`는 가변 인자 함수라서 컴파일러가 인자 타입을 맞춰 주지 않는다. **포맷 지정자와 인자 타입이 정확히 일치**해야 한다.
  - `%d` → `int`, `%X` → `unsigned int`, `%p` → **`void *`**
- `%p`에 `void *`가 아닌 포인터를 넘기는 것은 표준상 **UB**.
- x86-64에서는 모든 데이터 포인터 크기가 같아서 캐스팅 없이도 보통 정상 출력되지만,
  - `-Wall` 컴파일 시 경고 발생
  - 포인터 표현이 다른 플랫폼(일부 임베디드 등)에서는 잘못된 값이 나올 수 있음

👉 **어디서든 맞는 코드**를 위해 `(void *)`를 붙인다. 컴파일할 때 `gcc -Wall hello.c -o hello`처럼 `-Wall`을 붙이는 습관을 들이자.

## 4. 실수 연산이 정수보다 느린 이유

실수(IEEE 754)는 **부호 + 지수 + 가수**로 구성되어 있어서 연산 전후로 맞춰야 할 단계가 많다.

### float 덧셈 과정 (예: `1.5 + 0.375`)

```
1.5   = 1.100 × 2^0
0.375 = 1.100 × 2^-2
```

1. **지수 맞추기(정렬)**: 작은 쪽 가수를 시프트 → `0.011 × 2^0`
2. **가수 더하기**: `1.100 + 0.011 = 1.111`
3. **정규화**: 결과를 `1.xxx × 2^n` 꼴로 맞춤 (시프트 + 지수 조정)
4. **반올림**: 가수 비트 수(float은 23비트)에 맞춤. 반올림으로 자리올림이 생기면 재정규화
5. **예외 처리**: 오버플로(∞), 언더플로, NaN, 0 등

정수 덧셈은 2번만 하면 끝난다.

### 실제 차이

| 환경 | 정수 덧셈 | 실수 덧셈 |
|---|---|---|
| 최신 x86/ARM (FPU 있음) | 약 1클럭 | 약 3~4클럭 지연 |
| FPU 없는 MCU (Cortex-M0 등) | 1클럭 | 소프트웨어 에뮬레이션, 수십~수백 클럭 |

- FPU가 있으면 파이프라인 덕분에 처리량 차이는 크지 않다.
- **FPU 없는 임베디드 환경에서는 차이가 크다** → **고정소수점(fixed-point)** 사용 (예: 23.45도를 `2345`로 저장).
- **비정규수(subnormal)**: 0에 매우 가까운 값. 많은 CPU에서 연산 하나에 100클럭 이상 걸릴 수 있음 → FTZ/DAZ 모드로 0 처리하기도 함.

## 5. 정수 승격과 `char` 오버플로

```c
char x = 127;
char y = x + 1;
printf("%d %d %d\n", x, x + 1, y);
```

결과 (x86, gcc):

```
127 128 -128
```

| 식 | 값 | 이유 |
|---|---|---|
| `x` | 127 | 그대로 |
| `x + 1` | 128 | `char`가 **`int`로 승격(integer promotion)**된 뒤 연산 → int 범위 안 |
| `y` | -128 | int 128을 `char`에 **대입할 때** 하위 8비트만 남음 → `1000 0000` = -128 |

```
128 = 0000 0000 ... 1000 0000   (int, 32비트)
                    1000 0000   (char에 들어가는 8비트) → -128
```

반대 방향도 같다 (교재 01-11a).
```c
x = -128;
y = x - 1;
printf("x = %d, x - 1 = %d, y = %d\n", x, x - 1, y);
// x = -128, x - 1 = -129, y = 127
```
```
-129 = 1111 1111 ... 0111 1111   (int)
                     0111 1111   (char) → 127
```
→ char 범위(-128 ~ 127)의 양 끝은 **한 바퀴 돌아 이어진다**.

### 포인트

- **연산은 `int`에서, 잘리는 건 대입할 때.**
- 범위 밖 값을 signed 타입으로 변환하는 것은 **구현 정의(implementation-defined)** 동작.
- `int` 자체의 오버플로(`INT_MAX + 1`)는 **UB** → 더 위험.
- **`char`의 부호는 플랫폼마다 다르다.** x86은 보통 signed, ARM은 기본 unsigned (→ `127 128 128`). 부호가 중요하면 `signed char`, `int8_t` 등으로 명시.
- 참고: `printf(x, x + 1, y)`처럼 첫 인자에 포맷 문자열이 없으면 동작하지 않는다.

## 6. 2의 보수

컴퓨터가 **음수를 비트로 표현하는 방법**.

### 만드는 법: 비트 반전 후 +1

```
 5        = 0000 0101
 비트 반전 = 1111 1010   (1의 보수)
 +1       = 1111 1011   ← -5
```

### 자리값으로 해석하기

```
자리값:  -128  64  32  16  8  4  2  1
```

맨 앞 비트(MSB)만 **-128**, 나머지는 양수.

| 비트 | 값 |
|---|---|
| `1111 1011` | -128 + 64 + 32 + 16 + 8 + 2 + 1 = **-5** |
| `1000 0000` | **-128** (최솟값) |
| `0111 1111` | **127** (최댓값) |
| `1111 1111` | **-1** |

→ 8비트 signed 범위: **-128 ~ 127** (음수가 하나 더 많음)

### 왜 2의 보수를 쓰나

**덧셈 회로 하나로 뺄셈까지 처리**할 수 있기 때문.

```
  5  = 0000 0101
+ -5 = 1111 1011
-----------------
     1 0000 0000  → 넘친 1은 버림 → 0
```

부호-절댓값 방식은 +0과 -0이 둘 다 생기고, 부호별로 회로를 따로 처리해야 해서 불편하다.

최댓값 + 1 → 최솟값으로 **한 바퀴 돈다** (`0111 1111` + 1 = `1000 0000` = -128).

## 7. 컴퓨터에서 뺄셈이 이루어지는 방식

`x - 1`은 **`x + (-1)`**로 바꿔서 덧셈으로 계산한다.

- -1은 **모든 비트가 1**: 8비트 `1111 1111`, 32비트 `0xFFFFFFFF`

```
   5  = 0000 0101
+ -1  = 1111 1111
------------------
      1 0000 0100   → 넘친 1 버림 → 4
```

### ALU 내부 동작 (`A - B`)

1. B의 비트를 전부 뒤집고 (NOT)
2. 최하위 캐리 입력에 1을 넣고 (+1)
3. A와 더한다

→ "반전 + 1"과 덧셈이 **한 번의 덧셈기 통과**로 끝난다. 뺄셈 전용 회로가 필요 없다. (x86의 `DEC`도 내부적으로 같은 덧셈기 사용)

### 같은 비트, 다른 해석

```
0 - 1 → 1111 1111
```

- signed로 읽으면 **-1**
- unsigned로 읽으면 **255** (32비트면 `UINT_MAX` = 4294967295)

⚠️ 흔한 버그:

```c
for (unsigned int i = n; i >= 0; i--)   // i는 절대 음수가 안 됨 → 무한 루프
```

## 8. `while(1)` vs `for(;;)`

- 둘 다 무한 루프이며 **컴파일 결과(어셈블리)가 동일** → 성능 차이 없음.

| | `for(;;)` | `while(1)` |
|---|---|---|
| 특징 | 조건식이 없어 무한 루프 의도가 문법으로 드러남 | 읽을 때 직관적 |
| 배경 | K&R 스타일, 오래된 C 코드에 많음. 일부 컴파일러의 "조건이 항상 참" 경고(MSVC C4127 등)를 피함 | 임베디드 메인 루프의 관용 표현 |

```c
int main(void) {
    init_hardware();
    while (1) {
        read_sensor();
        update_output();
    }
}
```

👉 **팀/프로젝트 스타일을 따르고, 혼자라면 하나로 통일.** 임베디드 예제와 벤더 샘플 코드는 대부분 `while(1)`.

## 오늘의 핵심 요약

- 메모리는 바이트 단위 주소, 다바이트 값은 **엔디언** 규칙으로 저장된다.
- 바이트 단위로 보려면 **`unsigned char *`**. 포인터 연산은 타입 크기만큼 움직인다.
- `%p`에는 **`(void *)`**, 컴파일은 **`-Wall`**.
- 실수 연산은 **정렬·정규화·반올림** 때문에 느리다. FPU 없는 MCU에선 고정소수점.
- 작은 정수는 **`int`로 승격**되어 연산되고, **대입할 때** 잘린다.
- 음수는 **2의 보수**, 뺄셈은 **반전 + 1 + 덧셈**.
